# 07. 안드로이드 사전 테스트 앱 PRD — Mock 통화 연동 확장판

> **문서 성격**: 제품 요구사항 정의서 (개발 착수용)  
> **작성 목적**: 팀의 Flutter 앱을 만들기 전에, **백엔드·DB·ATM 연동이 실제 스마트폰에서 동작하는지 검증**하고, 최종 보이스피싱 방지 앱의 **Wi‑Fi 기반 2대 스마트폰 Mock 통화 시나리오**까지 사전 검증한다.  
> **만드는 사람**: 지도교사 (팀 학생이 아님)  
> **버전**: 2.0 · 2026-10-05  
> **기존 문서 기준**: 1.0 · 2026-09-20

---

## 1. 프로젝트 방향

최종 결과물은 **AI 기반 보이스피싱·스미싱 방지 앱**이다.

기존 사전 테스트 앱은 다음 흐름을 먼저 검증하는 데 목적이 있었다.

```text
문자 공유 / 스피커폰 받아쓰기
        ↓
백엔드 분석 API
        ↓
위험 등급·점수·탐지 근거
        ↓
QR
        ↓
Raspberry Pi ATM
        ↓
출금 허용 / 차단
```

이번 버전에서는 실제 이동통신 전화의 통화 음성을 직접 가로채는 방식 대신, **Wi‑Fi로 연결된 두 대의 스마트폰이 Mock Phone 앱을 통해 통화를 시뮬레이션**하도록 확장한다.

```text
┌───────────────┐        Wi‑Fi        ┌───────────────┐
│ 스마트폰 A    │ ◀─────────────────▶ │ 스마트폰 B    │
│ Mock Phone    │    Mock 통화 음성    │ Mock Phone    │
│ 공격자 역할   │                      │ 피해자 역할   │
└───────┬───────┘                      └───────┬───────┘
        │                                      │
        │                                      │ 음성 분석
        │                                      ▼
        │                              ┌───────────────┐
        └─────────────────────────────▶│ 백엔드        │
                                       │ FastAPI        │
                                       │ STT / 분석     │
                                       │ 위험도 판단    │
                                       └───────┬───────┘
                                               │
                                               ▼
                                       위험 결과 / 경고
```

### 핵심 원칙

**백엔드(+DB)와 기존 프론트엔드의 연동 계약은 변경하지 않는다.**

즉, Mock 통화 기능은 새로운 별도 시스템을 만드는 것이 아니라 **기존 `/api/v1/analysis`를 사용하는 새로운 입력 경로**로 취급한다.

```text
기존 문자
   └─→ text
          ┐
기존 받아쓰기 ─→ text ─→ POST /api/v1/analysis ─→ 기존 DB
          │                                      │
Mock 통화 ─→ STT text ───────────────────────────┘
                                               ↓
                                      기존 위험 분석 결과
                                               ↓
                                        기존 QR / ATM
```

# 2. 왜 Mock 통화를 사용하는가

## 2-1. 실제 전화 통화 녹음 방식의 한계

일반 Android 앱은 이동통신 전화의 통화 음성을 자유롭게 캡처할 수 없다.

따라서 다음과 같은 구조는 본 프로젝트의 사전 테스트 앱에서 사용하지 않는다.

```text
Samsung Phone
    ↓
실제 이동통신 통화
    ↓
제3자 앱이 통화 음성을 자동 녹음
    ↓
AI 분석
```

이 구조는 Android 권한 및 제조사 정책의 제약을 받으며, 전시용 학생 프로젝트에서 안정적으로 구현하기 어렵다.

## 2-2. Mock 통화의 장점

두 스마트폰이 같은 Wi‑Fi에 연결되어 있다면 앱 내부에서 통화 환경을 직접 만들 수 있다.

```text
스마트폰 A                    스마트폰 B
┌────────────┐                ┌────────────┐
│ 전화 걸기   │ ── Wi‑Fi ──▶ │ 전화 받기   │
│ 공격자      │ ◀─ 음성 ───── │ 피해자      │
└────────────┘                └─────┬──────┘
                                    │
                                    ▼
                              음성 분석
                                    │
                                    ▼
                           "보이스피싱 의심"
```

이 방식은 실제 전화망을 사용하지 않으면서도 다음을 시연할 수 있다.

- 전화 걸기 / 받기
- 양방향 음성 통화
- 통화 중 음성 분석
- STT 결과 실시간 표시
- 위험 점수 변화
- 보이스피싱 경고
- 통화 종료 후 최종 분석
- 위험 결과에 따른 QR 생성
- QR → Raspberry Pi ATM 출금 차단

# 3. 이 앱이 아닌 것

| | |
|---|---|
| ❌ 실제 이동통신 전화 앱 | 실제 전화망을 사용하지 않는다 |
| ❌ 실제 통화 녹음 앱 | 이동통신 통화 녹음 권한을 우회하지 않는다 |
| ❌ Google Play 배포용 최종 앱 | APK를 직접 설치하여 검증한다 |
| ❌ 최종 전시용 UI | UI 완성도보다 연동 검증이 우선이다 |
| ❌ 새로운 백엔드 시스템 | 기존 FastAPI + DB 계약을 그대로 사용한다 |
| ❌ 새로운 ATM 프로토콜 | 기존 QR → ATM 연동을 그대로 사용한다 |
| ❌ 통신망용 전화 서비스 | Wi‑Fi 내부의 Mock 통화만 사용한다 |

# 4. 성공 기준

| # | 기준 | 확인 방법 |
|---|---|---|
| S1 | 실제 Android 폰에서 로그인하고 분석 결과를 받는다 | 위험 등급과 점수가 표시된다 |
| S2 | 문자 공유로 받은 텍스트가 기존 분석 API에서 DANGER로 판정된다 | 보이스피싱 문자를 공유 → 기존 결과 확인 |
| S3 | 두 대의 스마트폰에서 Mock 통화를 연결할 수 있다 | A가 B에게 전화를 걸고 B가 수락 |
| S4 | Mock 통화 음성이 양방향으로 전달된다 | A/B가 서로 대화 |
| S5 | Mock 통화 중 음성이 텍스트로 변환된다 | B 화면에 상대방 발화가 표시 |
| S6 | 보이스피싱 대본을 읽으면 기존 분석 API에서 위험 판정된다 | STT 결과 → `/api/v1/analysis` |
| S7 | 위험도가 높아질 때 사용자에게 즉시 경고한다 | 위험 문장 입력 후 경고 표시 |
| S8 | 위험 결과에서 기존 QR이 생성된다 | 기존 `session_id`를 QR로 표시 |
| S9 | QR을 Raspberry Pi ATM이 읽고 출금이 차단된다 | 50만원 선택 → 서보 동작 차단 |
| S10 | 일반 통화는 SAFE로 처리되고 QR이 나타나지 않는다 | 가족 간 일반 대화 |
| S11 | 기존 프론트엔드가 사용하는 API/DB 구조가 변경되지 않는다 | 기존 웹 프론트와 결과 비교 |
| S12 | 통화 종료 후에도 최종 분석 결과를 확인할 수 있다 | 통화 종료 → 최종 분석 |

**S3~S7이 이번 버전의 핵심 추가 검증이다.**

**S8~S9는 기존 프로젝트의 최종 안전장치 검증이므로 반드시 유지한다.**

# 8. 통화 연결 방식

## 8-1. 1차 구현 권장 방식

두 스마트폰이 같은 Wi‑Fi에 연결된 전시 환경을 전제로 한다.

```text
Phone A
   │
   │ 연결 요청
   ▼
FastAPI
   │
   │ 세션/연결 정보
   ▼
Phone B
```

실제 음성 전달 방식은 **WebRTC 기반 양방향 음성 통화**를 우선 검토한다.

```text
Phone A
   │
   │ WebRTC
   │
   ▼
Phone B
```

FastAPI는 통화 음성을 직접 중계하는 역할보다 **시그널링과 분석 서버 역할**을 우선 담당한다.

### 중요

WebRTC 통화와 서버 분석 음성 스트림은 별개의 경로로 설계할 수 있다.

```text
                  ┌── WebRTC ──▶ 상대방
마이크 음성 ──────┤
                  └── 분석 경로 ──▶ STT / 위험분석
```

이렇게 하면 **통화 자체의 지연을 최소화하면서 분석 기능을 별도로 검증**할 수 있다.

# 9. 음성 분석 요구사항

## 9-1. 통화 중 분석

통화 중 모든 음성을 한 번에 분석하지 않는다.

짧은 단위로 텍스트를 누적한다.

```text
음성
 ↓
STT
 ↓
부분 텍스트
 ↓
누적 텍스트
 ↓
분석 요청
 ↓
위험도 표시
```

예:

```text
1차:
"서울중앙지검 수사관입니다."

2차:
"선생님 명의의 계좌가 범죄에 연루되어"

3차:
"안전계좌로 이체하셔야 합니다."

최종:
"서울중앙지검 수사관입니다. 선생님 명의의
계좌가 범죄에 연루되어 안전계좌로
이체하셔야 합니다."
```

## 9-2. 기존 분석 API 우선 사용

Mock 통화 기능을 만들기 위해 새로운 위험 분석 API를 만들지 않는다.

기존 API:

```http
POST /api/v1/analysis
Authorization: Bearer <토큰>
Content-Type: application/json
```

```json
{
  "message": "STT로 변환된 통화 내용"
}
```

을 그대로 사용한다.

### 따라서 Mock 통화의 핵심은

> **음성을 기존 `/api/v1/analysis`가 이해할 수 있는 텍스트로 변환하여 전달하는 것**

이다.

# 10. API 계약

> **중요: 이 장의 기존 API 계약은 변경하지 않는다.**
>
> Mock 통화는 기존 분석 API의 새로운 입력 방식일 뿐이다.

## 10-1. 공통

- 모든 성공 응답은 `{"data": ...}` 로 감싸여 온다
- 모든 실패 응답은 `{"detail": {"code": "...", "message": "..."}}` 이다
- 사용자용 API는 `Authorization: Bearer <토큰>` 헤더가 필요하다
- 토큰 유효 시간은 12시간이다

---

## 10-2. 로그인

```http
POST /api/v1/auth/login
Content-Type: application/json
```

```json
{
  "username": "halmeoni",
  "password": "<시연 비밀번호>"
}
```

응답:

```json
{
  "data": {
    "access_token": "eyJ...",
    "token_type": "bearer"
  }
}
```

---

## 10-3. 서버 상태

```http
GET /health
```

설정 화면에서 연결 확인용으로 사용한다.

---

## 10-4. 분석 요청

```http
POST /api/v1/analysis
Authorization: Bearer <토큰>
Content-Type: application/json
```

```json
{
  "message": "[검찰청] 귀하의 계좌가 범죄에 연루되어..."
}
```

응답:

```json
{
  "data": {
    "analysis_id": 12,
    "risk_level": "DANGER",
    "risk_score": 100,
    "reasons": [
      "기관 사칭 표현 감지",
      "범죄 연루 언급 감지"
```

# 11. DB 연동 원칙

Mock 통화 때문에 DB 테이블을 새로 만드는 것을 1차 목표로 하지 않는다.

기존 분석 결과가 기존 DB에 정상적으로 저장되는지를 확인하는 것이 우선이다.

```text
Mock 통화
   ↓
STT
   ↓
text
   ↓
기존 /analysis
   ↓
기존 DB
   ↓
기존 analysis_id / session_id
```

### 통화 세션 정보

1차 버전에서는 다음을 앱의 메모리 상태로 관리해도 된다.

- 상대방 ID
- 통화 시작 시간
- 통화 종료 시간
- 누적 STT 텍스트
- 현재 위험 점수

**통화 이력 전용 DB 테이블 추가는 백엔드 담당 학생이 기존 DB 구조를 검토한 뒤 별도로 결정한다.**

즉, 이번 사전 테스트 앱의 필수 조건은 **기존 DB 구조 변경이 아니다.**

# 12. QR 및 ATM 연동

기존 구조를 그대로 유지한다.

## QR 데이터

```json
{
  "session_id": "VP-000012"
}
```

QR에는 위험 상세나 개인정보를 넣지 않는다.

ATM이 `session_id`를 이용해 서버에서 분석 결과를 조회하는 기존 방식을 유지한다.

## 표시 조건

```text
risk_level != SAFE
AND
session_id != null
        ↓
QR 표시
```

SAFE일 때는 QR을 표시하지 않는다.

# 17. 음성 분석의 구현 단계

학생들이 한 번에 WebRTC + STT + AI를 구현하지 않도록 단계적으로 개발한다.

| 단계 | 구현 | 성공 기준 |
|---|---|---|
| V1 | 두 기기 연결 | 상대 기기가 보인다 |
| V2 | 통화 요청/수락 | 연결 상태가 변경된다 |
| V3 | 양방향 음성 | 서로 목소리가 들린다 |
| V4 | STT | 말한 내용이 텍스트로 나온다 |
| V5 | 분석 API | 텍스트가 `/analysis`로 전달된다 |
| V6 | 위험 표시 | 점수와 등급이 화면에 표시된다 |
| V7 | 실시간 분석 | 통화 중 위험도가 갱신된다 |
| V8 | 통화 종료 분석 | 최종 결과가 표시된다 |
| V9 | QR | 위험 통화에서 QR이 생성된다 |
| V10 | ATM | 위험 QR로 출금이 차단된다 |

**V1~V6을 먼저 완성한 뒤 V7~V10으로 진행한다.**

# 18. 실시간 분석의 현실적인 구현 원칙

실시간 통화와 분석을 지나치게 복잡하게 결합하지 않는다.

권장 구조:

```text
             ┌───────────────┐
             │ 마이크 음성    │
             └───────┬───────┘
                     │
             ┌───────┴────────┐
             │                 │
             ▼                 ▼
       WebRTC 통화          STT/분석
             │                 │
             ▼                 ▼
          상대방          누적 텍스트
                               │
                               ▼
                       /api/v1/analysis
                               │
                               ▼
                         위험도 / 근거
```

### 이유

통화 음성 전달과 AI 분석을 완전히 하나의 스트림으로 묶으면 다음 문제가 동시에 발생한다.

- 음성 코덱 처리
- WebRTC 오디오 트랙 접근
- STT 스트리밍
- 분석 API 호출 빈도
- 네트워크 지연
- Android 오디오 라우팅

따라서 **통화 연결을 먼저 완성하고, 분석 경로를 별도로 연결하는 방식**으로 개발한다.

# 25. 제약과 알려진 한계

## 25-1. 실제 이동통신 통화 분석 앱이 아니다

이 프로젝트는 실제 전화 앱을 가로채는 방식이 아니다.

```text
실제 전화망
    X

Mock Phone
    O
```

따라서 프로젝트 설명에서도 다음과 같이 표현한다.

> **Wi‑Fi 기반 Mock 통화 환경에서 실시간 음성 분석을 검증하였다.**

"스마트폰의 실제 통화 내용을 자동 녹음했다"라고 표현하지 않는다.

---

## 25-2. WebRTC 오디오와 STT 연결이 가장 어려운 부분이다

WebRTC 자체는 양방향 통화를 담당한다.

하지만 분석 서버에 음성을 보내려면 별도의 분석 경로가 필요할 수 있다.

```text
WebRTC Audio Track
       │
       ├── 상대방 재생
       │
       └── STT 분석
```

Android WebRTC 구현에서 원시 오디오 데이터를 분석 경로로 가져오는 부분이 예상보다 복잡할 경우, **1차 테스트에서는 통화 음성과 분석용 음성 입력을 분리**할 수 있다.

즉:

```text
통화 음성 → WebRTC

분석 음성 → STT → /analysis
```

이 방식도 PRD의 핵심 목적을 충족한다.

---

## 25-3. STT 정확도

전시장에서는 다음 문제가 발생할 수 있다.

- 주변 소음
- 스마트폰 스피커 음량
- 상대방 발화 속도
- 한국어 고유명사
- "검찰청", "금융감독원" 등의 인식 오류

따라서 STT 결과를 화면에 표시하고, 최종 분석 결과를 확인할 수 있도록 한다.

---

## 25-4. 규칙 엔진의 한계

기존 규칙 엔진은 특정 표현에 강하지만 구어체에는 약할 수 있다.

예:

```text
"서울중앙지검 수사관입니다..."
```

→ 높은 위험도

하지만

```text
"저희 쪽에서 확인해 보니까 통장 쪽에
조금 문제가 있는 것 같아서요..."
```

→ 낮은 점수가 나올 가능성

따라서 이것은 앱의 오류가 아니라 **현재 분석 엔진의 한계**로 기록한다.

- `/health`
- 문자 공유
- 텍스트 직접 입력
- 기존 `/api/v1/analysis`
- 기존 DB
- 위험 등급
- 위험 점수
- 탐지 근거
- `session_id`
- QR
- Raspberry Pi ATM
- ATM 출금 차단
- 기존 Frontend와 API 결과 비교

변경되는 핵심 입력 방식은 다음과 같다.

```text
기존
스피커폰 → SpeechRecognizer → 텍스트

변경/확장
Mock Phone A
      ↕
    Wi‑Fi
      ↕
Mock Phone B
      ↓
음성 분석 / STT
      ↓
기존 /api/v1/analysis
```

기존 스피커폰 받아쓰기 기능은 **호환성 테스트용 보조 입력 방식**으로 남겨둘 수 있다.

